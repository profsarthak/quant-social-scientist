Reproducible Analysis with Quarto

  • Show All Code
  • Hide All Code
  • View Source

One file that holds your writing, your code and its results, so that anyone can rebuild every number from scratch. The way this whole encyclopedia is made.

If the numbers in a report were typed in by hand, nobody can check where they came from, including you six months later. A Quarto document keeps the writing and the code that produces every number, table and figure in one file, and rebuilding the file reruns the code. The report and the analysis become the same thing. This page is about the tool; the wider practice it serves (open data, preregistration, replication) is in open & reproducible science. Every page of this site, including this one, is a Quarto document.

TipWhere you probably came from — and what you need

You likely arrived from open & reproducible science, wanting to know how reproducibility is done in practice, or from the “Show the figure code” fold under a figure on this site, wondering how the code and the page fit together. The question you came with is probably “how does a document run its own code?”

You need: to recognise a few lines of R or Python, from getting started in R or Python for simulation & ML. You don’t need to have installed Quarto, or to know Markdown already; both are introduced here.

Why it matters

Reinhart tells the story of the Potti case: a cancer-genomics analysis whose results could not be reproduced. Two statisticians, Baggerly and Coombes, estimated they spent 2,000 hours working out what had been done. Part of the problem was ordinary practice, not fraud. Raw data gets edited, converted and merged, results are copied and pasted between files and spreadsheets by hand, and often the only record of those steps is someone’s memory. Reinhart’s remedy is to make every step automated, with the code available as the definitive record and combined with a description of its purpose (Reinhart 2015). That is what a Quarto document is.

The idea in words

Think of a recipe card that cooks itself. The card has the instructions in plain language, and next to each step the exact actions to perform. Hand it to anyone with the same kitchen and they get the same dish.

  • A Quarto file (ending .qmd) is plain text with three kinds of content: a short header of settings at the top, ordinary prose, and code chunks (Wickham et al. 2023).
  • Rendering the file runs every chunk from top to bottom, in a fresh session, and pastes each result (a number, a table, a figure) into the finished page, which can be HTML, PDF or Word.
  • Change the data or the model and render again: every number in the text updates. There is no step at which a stale number, copied by hand, can survive.

R for Data Science names three uses for such a document: communicating with decision makers who want the conclusions, collaborating with analysts (including your future self) who want to see how you reached them, and working as a modern lab notebook that records what you did and what you were thinking (Wickham et al. 2023).

One small document, rendered

R for Data Science opens its chapter with a short report on the diamonds dataset (Wickham et al. 2023). Here it is in Quarto form (the book’s original is an R Markdown .Rmd file, Quarto’s predecessor; the ideas are the same and only the spelling of the options differs):

---
title: "Diamond sizes"
date: 2016-08-25
format: html
---

```{r}
#| include: false
library(ggplot2)
library(dplyr)
smaller <- diamonds |> filter(carat <= 2.5)
```

We have data about `{r} nrow(diamonds)` diamonds. Only
`{{r}} nrow(diamonds) - nrow(smaller)` are larger than 2.5 carats.
The distribution of the remainder is shown below:

```{r}
#| echo: false
ggplot(smaller, aes(carat)) + geom_freqpoly(binwidth = 0.01)
```

What happens when you render it, piece by piece:

  1. The header (between the --- lines) is written in YAML, a simple settings format. It sets the title, the date, and the output format.
  2. The first chunk loads two packages and makes smaller, the diamonds of 2.5 carats or less. The option include: false means it runs but neither the code nor any output appears in the report: it is set-up.
  3. The sentence contains two pieces of inline code. On rendering, they are replaced by their values: the reader sees “We have data about 53940 diamonds. Only 126 are larger than 2.5 carats.” (Wickham et al. 2023). If the dataset is updated, the sentence updates with it.
  4. The last chunk draws the plot. The option echo: false shows the figure but hides the code, which suits a reader who does not want to see R.
  5. The result is one self-contained HTML page. The .qmd file is the full record of how every number in it was made.
NoteJargon key — open if a term is unfamiliar
  • Markdown — a plain-text way of writing formatted text: # Heading, *italic*, - bullet.
  • YAML header — the block of key: value settings between --- lines at the top of the file.
  • Code chunk — a fenced block of code that runs when the document is rendered.
  • Chunk option — a #| line at the top of a chunk that controls whether it runs and what is shown.
  • Inline code — a short expression inside a sentence, replaced by its value on rendering.
  • Render — run all the code and build the finished page; R Markdown calls this knitting.
  • Engine — the program that actually runs the chunks: knitr for R, Jupyter for Python. Quarto passes the result to pandoc, which writes the output format (Wickham et al. 2023).
  • Cache / freeze — saved results from an earlier run, reused so expensive code is not rerun every time.
  • Seed — the number that fixes a random-number generator’s stream, so random results repeat exactly.
  • Working directory — the folder a running program treats as “here” when it opens files.

Prose, code, and output in one file

A Quarto document (.qmd) is Markdown with two additions: a YAML header for metadata, and code chunks that execute and drop their output inline. (Wickham et al. 2023)

---
title: "Wage gaps, revisited"
format: html
---

We fit a simple model and read off the gap.

```{r}
m <- lm(wage ~ educ + female, data = survey)
coef(m)["female"]
```

Render it and the code runs, the result is captured, and prose + output become one HTML (or PDF, or Word) page. Change the data or the model, re-render, and the narrative updates itself — there is no copy-paste step where a stale number can survive. That closed loop is reproducibility. (Wickham et al. 2023)

Chunk options control what the reader sees

Each chunk carries options (the #| lines) that decide what appears — code, output, figures, warnings: (Wickham et al. 2023)

#| label: fig-gap
#| fig-cap: "The estimated wage gap."
#| echo: false        # run the code but hide it
#| warning: false      # suppress warnings from the output

The ones you will use most, as R for Data Science lists them (Wickham et al. 2023):

Option Runs the code? Shows the code? Shows the results?
eval: false no yes no (nothing to show)
include: false yes no no
echo: false yes no yes
warning: false / message: false yes yes yes, without warnings / messages
error: true yes, and keeps going after an error yes yes, including the error

In plain words: eval: false displays example code without running it; include: false runs set-up code silently; echo: false is for reports whose readers want results, not code. By default a single error stops the render, which is what you want in a finished report; error: true is for debugging.

This is why the figures in this encyclopedia default to folded code (code-fold: true): the plot shows, the code is one click away — reproducible and readable.

freeze: cache the expensive execution

Re-running every simulation on every render is wasteful, and worse, it needs the full toolchain (R, Python, their packages) on whatever machine builds the site. Quarto’s freeze stores each document’s executed results in a _freeze/ folder; a document only re-executes when its own source changes. This site sets freeze: auto and commits _freeze/, so the public build renders from cached results without needing Python at all — the reason a plain static host can serve computed figures.

R Markdown’s equivalent is the chunk option cache = TRUE, and R for Data Science’s warning about it applies to both. Normally each render starts from a clean slate, which is good for reproducibility. A cache trades some of that away: it checks whether the code has changed, not whether the data the code reads has changed (Wickham et al. 2023).

In plain words: if you edit the file survey.csv but not the .qmd, a frozen document will happily show you last week’s results. Re-render that document deliberately (or clear the cache) when its inputs change.

The render → publish loop

quarto render          # execute changed docs, build the whole site into _site/
quarto preview         # live-reloading local preview while you write

From there, _site/ is static files: push them to any host. This project wraps that in a script that renders, mirrors _site to a public repo, and pushes — the same loop, automated.

When a document renders differently from how it behaved in your interactive session, R for Data Science’s first step is to restart and run every chunk in order, from a clean session. The most common difference is the working directory: a rendering document treats its own folder as “here” (Wickham et al. 2023).

Reproducibility has a mechanism: the seed

Any analysis with randomness — a simulation, a bootstrap, a train/test split — is only reproducible if the random numbers are. Setting a seed makes a pseudo-random stream deterministic: same seed, same draws, every run, every machine. Every figure in this encyclopedia seeds its generator for exactly this reason. The bootstrap in Python for simulation & ML gives a standard error of 4.902 for anyone who runs it with seed 42.

Show the figure code 
import numpy as np
import matplotlib.pyplot as plt

def walk(rng, n=250):
    return np.cumsum(rng.normal(size=n))

# same seed, two separate generators -> identical streams
a = walk(np.random.default_rng(42))
b = walk(np.random.default_rng(42))
assert np.array_equal(a, b)          # reproducibility, proven

# no shared seed -> different every run
c = walk(np.random.default_rng(1))
d = walk(np.random.default_rng(7))

fig, (axL, axR) = plt.subplots(1, 2, figsize=(8.4, 3.9), sharey=True)

axL.plot(a, color="#161613", lw=3.0, label="run 1")
axL.plot(b, color="#e8531d", lw=1.5, ls=(0, (5, 4)), label="run 2 (same seed)")
axL.set_title("Same seed → identical", fontsize=10)
axL.legend(fontsize=8.5, frameon=False, loc="upper left")

axR.plot(c, color="#161613", lw=2.0, label="run 1")
axR.plot(d, color="#8a8a7e", lw=2.0, label="run 2 (different seed)")
axR.set_title("No shared seed → different", fontsize=10)
axR.legend(fontsize=8.5, frameon=False, loc="upper left")

for ax in (axL, axR):
    ax.set_xlabel("step")
axL.set_ylabel("cumulative value")
fig.suptitle("Reproducibility is a property of seeded computation", fontsize=11)
fig.tight_layout()
plt.show()

Notebook habits

R for Data Science adapts advice on physical lab notebooks to analysis notebooks (Wickham et al. 2023). The tips that matter most:

  • Give each notebook a descriptive title, a clear file name, and a first paragraph stating the aims.
  • Record the start date in the header, in YYYY-MM-DD form so it cannot be misread.
  • When an idea turns out to be a dead end, keep it, with a short note on why it failed, so you don’t go down it again.
  • If you find an error in a data file, never edit the file by hand. Write code that corrects the value, and explain why.
  • Before stopping for the day, check the whole notebook still renders (clearing any cache).
  • Record the versions of the packages you used, so the analysis can be rerun next year.

Common pitfalls

WarningWhere reproducibility quietly breaks

  • Hidden state from out-of-order execution. Running chunks interactively in a different order than they appear lets a result depend on something defined below it. The fix is the discipline Quarto enforces on render: top-to-bottom, from a clean session. If it only works in your console, it is not reproducible.

  • Unseeded randomness. A bootstrap or simulation without a seed gives a different answer every render — the figure above is the whole argument. Seed it. (Kaplan 2024)

  • A cache that doesn’t know the data changed. A cached or frozen result is reused as long as the code is unchanged, even if a file it reads has changed (Wickham et al. 2023). Re-render on purpose after updating data.

  • Absolute paths. read_csv("C:/Users/me/data.csv") runs on exactly one machine. Use project-relative paths so the document travels.

  • Forgetting to commit _freeze/. If the cache is gitignored, a machine without the full toolchain cannot rebuild the site. Commit it (this project does) — or accept that every builder needs R/Python installed.

  • Environment drift. “Reproducible” up to package versions: a result can shift when a dependency updates. Record versions for analyses that must survive the years. R for Data Science’s quick fix is a chunk that runs sessionInfo(), which records the versions even if it cannot reinstall them; tools that store or reinstall the exact packages are the rigorous fix (Wickham et al. 2023).

## The idea in words {#sec-idea}

Think of a recipe card that cooks itself. The card has the instructions in plain language, and next to each
step the exact actions to perform. Hand it to anyone with the same kitchen and they get the same dish.

- A Quarto file (ending `.qmd`) is plain text with three kinds of content: a short **header** of settings at
  the top, ordinary **prose**, and **code chunks** [@wickham_r4ds].
- **Rendering** the file runs every chunk from top to bottom, in a fresh session, and pastes each result
  (a number, a table, a figure) into the finished page, which can be HTML, PDF or Word.
- Change the data or the model and render again: every number in the text updates. There is no step at
  which a stale number, copied by hand, can survive.

R for Data Science names three uses for such a document: communicating with decision makers who want the
conclusions, collaborating with analysts (including your future self) who want to see how you reached them,
and working as a modern lab notebook that records what you did and what you were thinking [@wickham_r4ds].

## One small document, rendered {#sec-by-hand}

R for Data Science opens its chapter with a short report on the `diamonds` dataset [@wickham_r4ds]. Here it
is in Quarto form (the book's original is an R Markdown `.Rmd` file, Quarto's predecessor; the ideas are the
same and only the spelling of the options differs):

````markdown
---
title: "Diamond sizes"
date: 2016-08-25
format: html
---

```{r}
#| include: false
library(ggplot2)
library(dplyr)
smaller <- diamonds |> filter(carat <= 2.5)
```

We have data about `{r} nrow(diamonds)` diamonds. Only
`{{r}} nrow(diamonds) - nrow(smaller)` are larger than 2.5 carats.
The distribution of the remainder is shown below:

```{r}
#| echo: false
ggplot(smaller, aes(carat)) + geom_freqpoly(binwidth = 0.01)
```
````

What happens when you render it, piece by piece:

1. **The header** (between the `---` lines) is written in **YAML**, a simple settings format. It sets the
   title, the date, and the output format.
2. **The first chunk** loads two packages and makes `smaller`, the diamonds of 2.5 carats or less. The
   option `include: false` means it runs but neither the code nor any output appears in the report: it is
   set-up.
3. **The sentence** contains two pieces of **inline code**. On rendering, they are replaced by their values:
   the reader sees "We have data about 53940 diamonds. Only 126 are larger than 2.5 carats."
   [@wickham_r4ds]. If the dataset is updated, the sentence updates with it.
4. **The last chunk** draws the plot. The option `echo: false` shows the figure but hides the code, which
   suits a reader who does not want to see R.
5. The result is one self-contained HTML page. The `.qmd` file is the full record of how every number in it
   was made.

::: {.callout-note collapse="true" title="Jargon key — open if a term is unfamiliar"}
- **Markdown** — a plain-text way of writing formatted text: `# Heading`, `*italic*`, `- bullet`.
- **YAML header** — the block of `key: value` settings between `---` lines at the top of the file.
- **Code chunk** — a fenced block of code that runs when the document is rendered.
- **Chunk option** — a `#|` line at the top of a chunk that controls whether it runs and what is shown.
- **Inline code** — a short expression inside a sentence, replaced by its value on rendering.
- **Render** — run all the code and build the finished page; R Markdown calls this **knitting**.
- **Engine** — the program that actually runs the chunks: **knitr** for R, **Jupyter** for Python. Quarto
  passes the result to **pandoc**, which writes the output format [@wickham_r4ds].
- **Cache / freeze** — saved results from an earlier run, reused so expensive code is not rerun every time.
- **Seed** — the number that fixes a random-number generator's stream, so random results repeat exactly.
- **Working directory** — the folder a running program treats as "here" when it opens files.
:::

## Prose, code, and output in one file

A Quarto document (`.qmd`) is Markdown with two additions: a **YAML header** for metadata, and **code chunks**
that execute and drop their output inline. [@wickham_r4ds]

````markdown
---
title: "Wage gaps, revisited"
format: html
---

We fit a simple model and read off the gap.

```{r}
m <- lm(wage ~ educ + female, data = survey)
coef(m)["female"]
```
````

Render it and the code runs, the result is captured, and prose + output become one HTML (or PDF, or Word) page.
Change the data or the model, re-render, and the narrative updates itself — there is no copy-paste step where a
stale number can survive. That closed loop *is* reproducibility. [@wickham_r4ds]

## Chunk options control what the reader sees {#sec-options}

Each chunk carries options (the `#|` lines) that decide what appears — code, output, figures, warnings:
[@wickham_r4ds]

```r
#| label: fig-gap
#| fig-cap: "The estimated wage gap."
#| echo: false        # run the code but hide it
#| warning: false      # suppress warnings from the output
```

The ones you will use most, as R for Data Science lists them [@wickham_r4ds]:

| Option | Runs the code? | Shows the code? | Shows the results? |
|---|---|---|---|
| `eval: false` | no | yes | no (nothing to show) |
| `include: false` | yes | no | no |
| `echo: false` | yes | no | yes |
| `warning: false` / `message: false` | yes | yes | yes, without warnings / messages |
| `error: true` | yes, and keeps going after an error | yes | yes, including the error |

> **In plain words:** `eval: false` displays example code without running it; `include: false` runs set-up
> code silently; `echo: false` is for reports whose readers want results, not code. By default a single error
> stops the render, which is what you want in a finished report; `error: true` is for debugging.

This is why the figures in this encyclopedia default to **folded** code (`code-fold: true`): the plot shows, the
code is one click away — reproducible *and* readable.

## `freeze`: cache the expensive execution {#sec-freeze}

Re-running every simulation on every render is wasteful, and worse, it needs the full toolchain (R, Python,
their packages) on whatever machine builds the site. Quarto's **`freeze`** stores each document's executed
results in a `_freeze/` folder; a document only re-executes when *its own source changes*. This site sets
`freeze: auto` and commits `_freeze/`, so the public build renders from cached results without needing
Python at all — the reason a plain static host can serve computed figures.

R Markdown's equivalent is the chunk option `cache = TRUE`, and R for Data Science's warning about it applies
to both. Normally each render starts from a clean slate, which is good for reproducibility. A cache trades some
of that away: it checks whether the *code* has changed, not whether the data the code reads has changed
[@wickham_r4ds].

> **In plain words:** if you edit the file `survey.csv` but not the `.qmd`, a frozen document will happily
> show you last week's results. Re-render that document deliberately (or clear the cache) when its inputs
> change.

## The render → publish loop {#sec-render}

```bash
quarto render          # execute changed docs, build the whole site into _site/
quarto preview         # live-reloading local preview while you write
```

From there, `_site/` is static files: push them to any host. This project wraps that in a script that renders,
mirrors `_site` to a public repo, and pushes — the same loop, automated.

When a document renders differently from how it behaved in your interactive session, R for Data Science's
first step is to restart and run every chunk in order, from a clean session. The most common difference is
the **working directory**: a rendering document treats its own folder as "here" [@wickham_r4ds].

## Reproducibility has a mechanism: the seed {#sec-seed}

Any analysis with randomness — a simulation, a bootstrap, a train/test split — is only reproducible if the
random numbers are. Setting a **seed** makes a pseudo-random stream deterministic: same seed, same draws, every
run, every machine. Every figure in this encyclopedia seeds its generator for exactly this reason. The
bootstrap in [Python for simulation & ML](python-for-sim-and-ml.qmd#sec-by-hand) gives a standard error of
4.902 for anyone who runs it with seed 42.

```{python}
#| label: fig-seed
#| fig-cap: "Why every figure here is seeded. Left: two independent runs of the same random walk with the same seed (default_rng(42)) — the dashed second run traces the first exactly, so you see one line; the code asserts the two arrays are byte-identical. Right: two runs with no shared seed diverge completely. Reproducibility is not a property of careful people; it is a property of seeded computation. A reader who reruns this document gets pixel-identical figures."
#| code-fold: true
#| code-summary: "Show the figure code"

import numpy as np
import matplotlib.pyplot as plt

def walk(rng, n=250):
    return np.cumsum(rng.normal(size=n))

# same seed, two separate generators -> identical streams
a = walk(np.random.default_rng(42))
b = walk(np.random.default_rng(42))
assert np.array_equal(a, b)          # reproducibility, proven

# no shared seed -> different every run
c = walk(np.random.default_rng(1))
d = walk(np.random.default_rng(7))

fig, (axL, axR) = plt.subplots(1, 2, figsize=(8.4, 3.9), sharey=True)

axL.plot(a, color="#161613", lw=3.0, label="run 1")
axL.plot(b, color="#e8531d", lw=1.5, ls=(0, (5, 4)), label="run 2 (same seed)")
axL.set_title("Same seed → identical", fontsize=10)
axL.legend(fontsize=8.5, frameon=False, loc="upper left")

axR.plot(c, color="#161613", lw=2.0, label="run 1")
axR.plot(d, color="#8a8a7e", lw=2.0, label="run 2 (different seed)")
axR.set_title("No shared seed → different", fontsize=10)
axR.legend(fontsize=8.5, frameon=False, loc="upper left")

for ax in (axL, axR):
    ax.set_xlabel("step")
axL.set_ylabel("cumulative value")
fig.suptitle("Reproducibility is a property of seeded computation", fontsize=11)
fig.tight_layout()
plt.show()
```

## Notebook habits {#sec-habits}

R for Data Science adapts advice on physical lab notebooks to analysis notebooks [@wickham_r4ds]. The tips that
matter most:

- Give each notebook a descriptive title, a clear file name, and a first paragraph stating the aims.
- Record the start date in the header, in `YYYY-MM-DD` form so it cannot be misread.
- When an idea turns out to be a dead end, keep it, with a short note on why it failed, so you don't go down
  it again.
- If you find an error in a data file, never edit the file by hand. Write code that corrects the value, and
  explain why.
- Before stopping for the day, check the whole notebook still renders (clearing any cache).
- Record the versions of the packages you used, so the analysis can be rerun next year.

## Common pitfalls

::: {.callout-warning title="Where reproducibility quietly breaks"}

- **Hidden state from out-of-order execution.** Running chunks interactively in a different order than they
  appear lets a result depend on something defined *below* it. The fix is the discipline Quarto enforces on
  render: **top-to-bottom, from a clean session.** If it only works in your console, it is not reproducible.

- **Unseeded randomness.** A bootstrap or simulation without a seed gives a different answer every render — the
  figure above is the whole argument. Seed it. [@kaplan_lessons]

- **A cache that doesn't know the data changed.** A cached or frozen result is reused as long as the code is
  unchanged, even if a file it reads has changed [@wickham_r4ds]. Re-render on purpose after updating data.

- **Absolute paths.** `read_csv("C:/Users/me/data.csv")` runs on exactly one machine. Use project-relative
  paths so the document travels.

- **Forgetting to commit `_freeze/`.** If the cache is gitignored, a machine without the full toolchain cannot
  rebuild the site. Commit it (this project does) — or accept that every builder needs R/Python installed.

- **Environment drift.** "Reproducible" up to package versions: a result can shift when a dependency updates.
  Record versions for analyses that must survive the years. R for Data Science's quick fix is a chunk that
  runs `sessionInfo()`, which records the versions even if it cannot reinstall them; tools that store or
  reinstall the exact packages are the rigorous fix [@wickham_r4ds].

:::

::: {.callout-note collapse="true" title="Who says what"}
- **Wickham & Grolemund, *R for Data Science*, chapters 21–24 (R Markdown)** — the literate document (YAML
  header, Markdown, code chunks), the three uses (communicate, collaborate, lab notebook), the `diamonds`
  example with inline code (53,940 diamonds, 126 above 2.5 carats), knitr → pandoc, chunk options (`eval`,
  `include`, `echo`, `message`/`warning`, `error`), caching and its blind spot for changed files,
  troubleshooting from a clean session and the working directory, and the lab-notebook tips including
  `sessionInfo()`. The corpus copy is the first edition, which teaches R Markdown; Quarto is its successor,
  and the `#|` option syntax and `freeze` on this page are Quarto's, not the book's.
- **Reinhart, *Statistics Done Wrong*** — the Potti case and Baggerly & Coombes's 2,000 hours; error-prone
  hand copying between files; reproducible analysis as automated steps with the code as the definitive record
  (Sweave and the IPython Notebook as early tools).
- **Kaplan, *Lessons in Statistical Thinking*** — the case that computation (and its randomness) must be
  reproducible to be trustworthy, and the seed as the mechanism.
- **This repository** — a live example: `freeze: auto` with a committed `_freeze/`, a render → mirror → push
  script, and every figure seeded.
- *The self-cooking recipe card is this encyclopedia's own picture.* An earlier version of this page cited
  "the Quarto chapters" of *R for Data Science*; those are in the second edition, not the corpus copy.
